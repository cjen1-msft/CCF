Event-to-action reductions

One C++ event need not equal one Lean action

A helper event can add no action. One aggregate packet can add several actions. The certificate records both cases.

C++ events 9 through 20

Use the event list to highlight its Lean action or action span.

Why span start and aggregate fields differ

Event 9 observes one C++ batch for absolute indices 1 through 3. Lean sends one entry per action, so the batch expands to append ends 1, 2, and 3. Event 11 similarly expands one aggregate follower receive into three receives. Event 20 expands the aggregate response into response receives for 1, 2, and 3.

The C++ event's state fields describe the state before the aggregate operation, so they constrain the span start. Packet range, destination, and aggregate result fields describe the batch as a whole, so they constrain all actions or the span end. Helper records such as execute_append_entries_sync, commit, and send_append_entries_response remain assertions inside the owning receive. They do not invent extra model actions.

Existential formula

Find one complete bounded explanation

The formula chooses a start state and every hidden value. Observations and bounded transition equations constrain those choices.

Current lowering versus long-term proved lowering

The current generator emits a hand-maintained bounded encoding. Lean does not prove that this formula is equivalent to CCFRaft.Model. SAT therefore supplies a candidate that Lean must check. UNSAT cannot reject the implementation trace.

The long-term design needs a proved lowering or a proved automatic footprint extraction and lowering path. That future proof is separate from this prototype result.

SAT witness

Decode solver values before trusting them

cvc5 returns SAT. The decoder materializes every state, action, log, queue, and observed field in a JSON witness.

What cvc5 selected

The unknown transaction representative is 1 : Fin 64. S0 has node 0 as term-2 leader with log length 2 and commit 0. Node 1 is inert in the cheap world. The model fills all state and queue values through S43.

Where the witness ends

At S43, nodes 0 and 1 both have log length 7 and commit index 7. Both cheap queues are empty. The canonical completion later checks all 15 destination queues as drained.

SAT means that the generated bounded formula has a model. The SAT result alone does not mean that system.applyAction accepts the decoded actions.

Current checker shape. The prototype writes 4,298 lines and 382,143 bytes of witness-specific Lean source. About 70 seconds is compilation and checking of that generated source, not replay-only time. Profiling points to the six generated span functions, especially events 9 and 11. The intended generic precompiled checker reads witness data without recompiling these declarations.
What the Lean check does not prove

The checker does not prove Reachable S0. It also does not construct the proof-only histories required by SystemInductiveInvariant S0. Those missing premises prevent the valid segment from becoming a reachable-safety theorem.

Concrete negative control: commit violation

Event 53 observes node 0 at commit index 7 before the final response receive. The mutation changes that checkpoint to commit index 6 at S42 while retaining action 40 advanceCommitIndex and actions 41 and 42 for the final append and receive. cvc5 returns UNSAT. The test proves that the bounded formula notices this in-domain contradiction. It does not prove that every possible commit violation is impossible in the full model.
