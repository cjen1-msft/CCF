Investigation report / 24 August 2026

Consistency traces need reconstruction; CCFRaft traces do not

Amaury's branch contains a complete runtime-to-Lean consistency validator. Python reconstructs omitted ledger and view operations, emits exact Lean actions, and Lean proves the resulting execution reachable. CCFRaft starts one layer later: its trace already is an exact model-action sequence.

01 / Direct answer

Yes, the Lean validator exists upstream

It is not in this branch or in microsoft/CCF. The most complete implementation is on achamayou/vl-consistency. A standalone pure-Lean variant is on achamayou/pure-lean-consistency.

Implemented

Runtime to Lean reachability

Strict NDJSON parsing, deterministic gap reconstruction, generated typed actions, guard checking, canonical transitions, and a kernel-checked Reachable theorem.

Unmerged

Branch status

vl-consistency is 26 commits ahead of its base and has no associated PR. The rollback fix for the TLA adapter did merge separately as PR #8133.

Not a full refinement proof

Claim boundary

Python's observation-to-plan translation is trusted as input generation. Lean proves that the generated actions form a reachable model execution, not that every CCF behavior refines the Lean model.

The shortest accurate summary TLC searches for hidden actions. Python chooses them for Lean. Lean checks the exact plan and proves reachability.
02 / Consistency trace pipeline

Click a stage to inspect the trust boundary

The runtime trace is partial. It records client-visible requests, executions, responses, and transaction statuses, but not every ledger append or view change.

1. Runtime NDJSON

tests/tvc.py emits one strict JSON object per client-visible event. The trace contains request IDs and observed [view, seqno] pairs, but omits internal ledger fillers and branch creation.

Outside the Lean trust boundary

  • Runtime instrumentation coverage.
  • Python parsing and rank normalization.
  • Choice of filler and truncation actions.
  • The claim that observations correspond to CCF semantics.

Kernel-checked

  • Every generated action guard holds.
  • Every successor uses the canonical Lean transition.
  • The complete action list starts at initialState.
  • The final state is Reachable.

One NDJSON stream, three validators

TLC

Searches

Reads the observations directly and explores omitted backfill and view-change steps. It needs breadth-first search, one worker, and disabled deadlock checking.

Veil

Replays a planned trace

Uses the same strict Python parser and planner, then validates the exact reconstructed action list against the Veil model.

Pure Lean

Proves reachability

Renders the plan as typed Lean values, checks every guard and canonical transition, then proves the final state reachable.

04 / CCFConsistency details

The planner creates the witness that Lean checks

The local model cannot execute directly. The upstream experiment adds a computable trace facade without replacing the canonical relational model.

Canonical model

Relational and proof-oriented

Ten ...Next functions define state updates. Step constructors carry their guards as proof premises. Reachable is their inductive closure.

Model transitions GitHub ref
Trace facade

Computable but canonical

TraceAction mirrors all ten actions. Enabled makes the guards decidable and next calls the canonical update functions. enabled_step reconnects execution to Step.

Trace.lean TraceInfra.lean
Rank normalization

The planner maps distinct observed transaction IDs, views, and sequence numbers to sorted ranks. Numeric gaps that never appear in observations disappear. Observed sequence numbers 197 and 199 may become ranks 0 and 1 with no filler between them.

This matches the Lean model's "next ordered identifier" guards, but it is an abstraction choice made by Python, not a theorem.

Planner and rank maps Sparse-ID tests
Rollback reconstruction

When a new view reuses a sequence number, the planner copies only entries strictly before that slot. It drops the uncommitted suffix, rejects truncation below a committed prefix, then fills any required gaps.

PR #8133 merged the equivalent fix into the TLA adapter. The Lean planner already used the prefix rule on vl-consistency.

05 / CCFRaft replay

The trace is already the certificate plan

CCFRaft traces use the same action vocabulary as the model. There is no hidden-state search or implementation-log projection.

CSV-like line append,0,1,2 or timeout,5.
parseAction Bounds IDs and creates one exact model action.
system.applyAction Checks Enabled, then calls next.
Regression checks Committed prefixes, signatures, log matching, terms, elections.
Final projection Terms, commits, leaders, configurations, joined nodes.

What is proved

applyAction and runActionsReachable connect successful action application to the same Step/Reachable system used by the preservation theorem.

What remains testing

The IO replay loop reports Boolean state checks. It does not reconstruct the proof-only invariant, prove render/parse round-trip, or connect these hand-written traces to runtime raft_trace NDJSON.

06 / Practical adoption

Bring the validator over as a vertical slice

The local proof and the upstream validator share a common ancestor, so this is integration work rather than a new design.

1 / Import

Take the pure-Lean trace facade

Bring in Trace.lean, TraceInfra.lean, and lean/trace_validation.py. Use pure-lean-consistency if you want the standalone planner copy; use vl-consistency to share the Veil parser and planner.

2 / Reconcile

Port onto the newer proof tree

Keep the local CCFConsistency.Model and proof exports authoritative. Resolve branch drift in action guards, generated imports, Lake targets, and the property-bundle name.

3 / Pin

Add deterministic fixtures

Check in the rollback and sparse-ID NDJSON fixtures. Make CI regenerate the Lean module, compile it with kernel reduction, and run the generic proof build separately.

07 / Claims and limits

What successful validation does and does not establish

Established for one trace
  • The strict parser accepted the logged projection.
  • The planner produced one exact action sequence.
  • Every action guard held under canonical Lean semantics.
  • The final replay state is reachable.
  • The generated theorem avoids forbidden proof escapes.
Not established
  • A general CCF-to-Lean refinement theorem.
  • Completeness of runtime instrumentation.
  • Correctness of Python reconstruction.
  • Equivalence between hand-written Lean, Veil, and TLA+.
  • All 36 translated consistency properties in the local proof.
Do not conflate the two trace pipelines add_make_traces_script and PR #5818 generate low-level Raft driver traces for Traceccfraft.tla. They are not inputs to the Lean consistency validator.
